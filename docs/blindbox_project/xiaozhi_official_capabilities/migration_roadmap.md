# 从小智官网依赖到自研平台的迁移路线

文档状态：draft  
主责智能体：架构师智能体  
更新时间：2026-07-13

## 0. 迁移原则

迁移不是一次性替换小智官网，而是分阶段把“业务控制权”迁回我方。

原则：

- 先迁业务数据，再迁工具管理，再迁设备接入，最后迁语音底座。
- 每一阶段都保留官网或固件兜底。
- 不为了转自研而影响一期 Demo。
- 所有迁移都围绕“一台设备绑定一个角色”这个核心关系展开。

## 1. 阶段路线

| 阶段 | 名称 | 目标 | 官网关系 |
| --- | --- | --- | --- |
| S0 | 当前一期 | 自研业务后台 + 官网语音/MCP 不可见依赖 | 官网承载语音和入口 |
| S1 | 设备配置中心 | 设备从我方拉取角色和景区配置 | 官网仍承载语音 |
| S2 | 角色控制台 | 角色 prompt、voice_id、知识库引用由我方统一维护 | 官网只保留必要同步 |
| S3 | MCP 工具管理 | 工具注册、参数、日志在我方管理 | 官网只是工具调用通道 |
| S4 | 设备接入增强 | 我方掌握设备心跳、配置版本、在线状态 | 官网仍可做语音连接 |
| S5 | OTA/固件包 | 我方管理固件版本、升级、回滚 | 官网能力可参考或兼容 |
| S6 | 语音服务私有化 | 自建或接入兼容小智服务端 | 官网变为备选通道 |

## 2. S1：设备配置中心

目标：

- 设备启动时从我方后端拉取配置。
- 配置包含绑定角色、景点、NFC 标签、数据集摘要、播报模板版本。
- 失败时使用本地缓存或固件静态配置。

建议接口：

- `GET /api/v1/devices/{device_id}/config`
- `POST /api/v1/devices/{device_id}/heartbeat`
- `POST /api/v1/devices/{device_id}/config-sync-result`

全栈落地边界：

- 后端实现配置聚合。
- 固件实现拉取和缓存。
- 前端展示配置版本和最后同步时间。

## 3. S2：角色控制台

目标：

- 我方作为角色配置源。
- 支持一个设备绑定一个角色。
- 支持 prompt、voice_id、知识库引用、启停状态。
- 管理端看起来和使用上以我方平台为准，小智官网只作为被同步的执行端。

建议能力：

- 角色 CRUD。
- 设备绑定/改绑角色。
- 配置预览。
- 角色上下文生成。
- 官网同步状态字段。
- prompt/personality/voice_id 配置版本。
- 一键生成“待同步到官网”的配置摘要，至少支持人工复制同步。
- 同步结果记录：未同步、已同步、同步失败、需要人工处理。

需要注意：

- 历史打卡记录保留当时的 `agent_id`，不能因改绑丢失语义。
- 官网侧如果仍需人工配置，必须记录“官网配置是否已同步”。
- 不在我方平台保存小智官网账号密码；如果需要自动同步，必须另走安全设计确认。

### 3.1 S2.5：对话记录与内容沉淀

用户确认的新目标：至少要让对话记录、对话内容、角色性格提示词和同步状态都能在我方自研平台体现。短期不要求完全接管实时语音链路，但管理端必须看起来是完整主控台。

建议能力：

- Conversation Session：一次设备会话或一次用户交互的会话记录。
- Conversation Message：用户输入、AI 回复、来源、时间、关联设备、关联角色、关联点位。
- Conversation Summary：会话摘要、关键词、失败原因、是否用于后续知识优化。
- Official Sync Snapshot：本次角色配置同步到小智官网时的 prompt、voice_id、工具入口和人工操作备注。
- Official Sync Status：每个角色/设备的官网同步状态、最后同步时间、操作人和失败原因。

落地边界：

- 如果当前无法从小智官网自动拉取完整对话，先支持手工导入、官网截图/文本摘录录入、设备侧/工具侧日志回填。
- 我方平台保存“能支撑演示和排障的对话摘要与内容”，不把官网作为主数据源。
- 对话记录页面需要能按设备、角色、时间、点位和来源筛选。
- 后续进入语音私有化后，再把实时 ASR/LLM/TTS 全量日志迁入我方平台。

## 4. S3：MCP 工具管理

目标：

- 不再完全依赖官网人工配置工具。
- 我方至少掌握工具定义、参数、调用日志和失败兜底。
- 小智官网仍可作为工具调用通道，但工具定义、参数说明、调用结果和错误日志在我方平台可见。

建议模块：

- Tool Registry：工具定义。
- Tool Binding：工具与角色/设备绑定。
- Tool Invocation Log：调用日志。
- Tool Test Console：本地测试工具调用。

建议优先工具：

- `get_agent_context`
- `search_scenic_knowledge`
- `report_checkin`
- `get_device_status`

## 5. S4：设备接入增强

目标：

- 我方掌握业务层设备在线状态和配置版本。
- 不要求立刻替代实时语音连接。

建议能力：

- 设备心跳。
- 在线/离线摘要。
- 最近配置版本。
- 最近打卡状态。
- token 校验。
- 异常设备列表。

边界：

- Django 不承载实时音频流。
- 语音 WebSocket/MQTT 仍可走小智或独立语音网关。

## 6. S5：固件包管理和 OTA

目标：

- 商业化前具备固件版本管理。
- 支持升级记录、灰度、失败回滚。

建议后置原因：

- OTA 风险高，设备异常会直接影响硬件可用性。
- 需要真实设备和稳定固件流程。
- 需要研发主管制定发布和回滚门禁。

## 7. S6：语音服务私有化

目标：

- 自建或接入兼容小智协议的服务端。
- 将 ASR/LLM/TTS 编排迁出官网。

启动前置条件：

- 设备配置中心稳定。
- 角色控制台稳定。
- MCP 工具管理稳定。
- 至少一轮真实硬件联调通过。
- 明确商业化要求不能依赖第三方官网。

## 8. 推荐近期执行

近期只建议推进到 S1-S3：

1. 设备配置中心。
2. 角色控制台。
3. MCP 工具管理。

OTA 和语音私有化不建议作为下一步第一批任务。

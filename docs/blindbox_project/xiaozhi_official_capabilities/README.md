当前建议采用双轨路线：

1. **自研替代轨**：逐步把设备配置、角色控制台、MCP 工具管理、景区业务数据、打卡记录迁到我方平台。
2. **官网回退轨**：如果某项自研能力短期不稳定，仍允许回退到 `xiaozhi.me` 官网能力或人工配置，保证 Demo 和联调不断。

这意味着：我们不是一次性切断小智官网，而是先把业务控制权收回来，同时保留可回退链路。

## 1. 当前一期定位

一期仍按已确认架构执行：

- 小智官网/官方链路负责语音入口、设备接入、语音服务和一期 MCP/工具入口。
- 我方自研后端负责角色配置源、景区知识库、设备绑定、GPS/NFC 打卡、演示后台。
- 对专家、领导和演示用户不展示小智官网页面，只展示我方管理端和演示页。
- 官网能力作为不可见依赖，不作为业务数据主库。

## 3. 自研替代优先级

### P0：必须先收回的业务控制权

- 设备业务档案。
- 一台设备绑定一个角色。
- 角色 prompt 源数据。
- 景区知识库。
- GPS/NFC 点位和打卡记录。
- 自研管理端和演示页。

这些是我们的产品差异和业务数据资产，不能长期只放在小智官网。

### P1：建议下一步建设

- 设备配置下发版本。
- MCP 工具管理页。
- 工具调用日志。
- 小智官网配置自动化辅助。
- 设备在线状态和心跳。
- 角色配置同步到官网的半自动流程。
- 对话记录、对话摘要和内容沉淀页面。
- 角色 prompt、性格、人设、voice_id 的配置版本与同步状态。

这些能力可以明显降低人工配置和官网依赖。

### 3.1 近期新增目标：自研主控台 + 官网同步桥

用户已确认近期需要达成的效果是：形式上所有配置和记录都在我方自研平台体现，小智官网只作为底层语音执行和被同步目标。

因此下一阶段不是马上私有化语音服务，而是先做：

- 我方平台管理角色性格提示词、prompt、voice_id、知识库引用。
- 我方平台保存对话记录、用户内容、AI 回复、摘要和失败原因。
- 我方平台记录哪些配置已同步到小智官网、何时同步、由谁同步、失败原因。
- 官网侧如果还要人工配置，也必须在我方平台留下同步快照和操作记录。
- 演示时只打开我方平台，尽量不展示小智官网页面。

这条路线可以先达到“看着完整、管控口径完整”的效果，同时保留官网语音链路，避免一下子跳到高风险语音私有化。

### P2：商业化前建设

- 设备激活。
- 配网引导。
- 固件包管理。
- OTA 灰度、回滚和失败恢复。
- 设备证书或动态 token。
- 多账号权限和操作审计。

这些能力进入真实批量设备后再建设，课题一期不抢。

### P3：重型私有化

- 自建小智兼容服务端。
- 自建语音网关。
- ASR/LLM/TTS 编排。
- 实时音频链路监控。
- 多模型、多音色、计费和限流。

这是“完全摆脱官网”的核心壁垒，不建议在业务控制台稳定前启动。

## 4. 双轨运行策略

```text
设备
  -> 语音链路优先走 xiaozhi.me
  -> 业务配置优先拉取我方 Django 后端
  -> MCP/工具入口可先配置在官网
  -> 工具实际调用我方后端接口
  -> 如果我方接口失败，回退固定播报/固件兜底配置
```

### 自研成功时

- 设备配置从我方后端稳定拉取。
- 角色、景区知识、NFC、打卡记录均在我方平台闭环。
- 官网只剩语音通道和临时工具入口。

### 自研未完成或不稳定时

- 设备仍可用小智官网语音链路。
- 角色 prompt 可临时人工配置在官网。
- 固件保留静态配置兜底。
- 景区问答失败时走固定播报文案。
- 打卡事件先本地记录或模拟器演示，后续补传。

## 5. 和小智官网的边界区别

小智官网偏平台底座：

- 设备接入。
- 语音链路。
- 模型/音色/智能体配置。
- MCP 工具入口。
- 官方控制台。

我方平台偏业务运营：

- 盲盒角色绑定。
- 景区数据和知识库。
- GPS/NFC 打卡。
- 打卡记录和演示看板。
- 面向课题/市场化的业务页面。

短期不追求像素级复刻官网；优先复刻和增强“我们商业化必须掌握的控制台能力”。

## 6. 技术壁垒

| 壁垒 | 难点 | 建议处理 |
| --- | --- | --- |
| 设备接入 | 长连接、心跳、掉线、鉴权、配置版本 | 先做 HTTP 配置拉取和心跳，再评估网关 |
| 语音私有化 | 实时音频、ASR、LLM、TTS、延迟、并发 | 暂不抢，先保留官网 |
| MCP 工具体系 | 工具注册、参数、权限、日志、失败兜底 | 下一阶段优先做管理页和调用日志 |
| OTA | 包管理、灰度、断电恢复、回滚 | 商业化前建设，不进一期 |
| 数据一致性 | 设备绑定、角色改绑、历史打卡不丢 | 后端模型先按长期关系设计 |
| 安全 | token、设备身份、官网调用我方接口 | 一期轻量 token，商业化再升级 |

## 7. 当前推荐结论

建议确认“双轨方案”：

- 一期继续保留小智官网作为语音和接入回退。
- 自研平台先完成业务配置、角色绑定、景区知识、GPS/NFC 打卡和演示页。
- 下一阶段优先建设“设备配置中心 + 角色控制台 + MCP 工具管理”。
- OTA 和自建语音服务端后置，等设备数量和商业化诉求明确后再启动。

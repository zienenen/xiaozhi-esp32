## 2. 已确认产品结论

| 编号 | 结论 | 当前影响 |
| --- | --- | --- |
| D-01 | 当前优先完成课题主线 | 课题一期 P0 优先于市场化完整商业闭环 |
| D-02 | 市场化方向需要保留 | 角色池、单设备单智能体、原厂绑定、管理端能力不能被破坏 |
| D-03 | 景区数据集/向量库管理页列为课题一期 P0 | 架构和全栈必须给出数据集状态展示与知识关联方案 |
| D-04 | 一期 Demo 只要求 1 个景点点位完整跑通 | 多点位配置放 P1，路线规划放 P2 |
| D-05 | 手动模拟打卡页进入一期 P0 | 无硬件或调试阶段可联调，模拟记录必须与真实记录区分 |
| D-06 | 课题一期采用 GPS 粗定位 + NFC 精准打卡 | GPS 只负责接近提醒，NFC 是打卡成功依据 |
| D-07 | 管理页面需要适配 PC、平板、手机 | 三端页面不能被整体推到二期 |
| D-08 | 每台硬件机器人只能绑定一个智能体 | 设备详情、绑定页、演示页状态必须一致 |
| D-09 | 后期只能由原厂后台更换绑定角色 | 普通用户不提供角色自由切换入口 |
| D-10 | 市场化目标用户为 18-26 岁潮玩用户 | 不以儿童/亲子作为市场化主线 |
| D-11 | 后期商业化需要逐步对标小智官网全部核心能力 | 研发主管需要按 P0/P1/P2/P3 拆解任务和评估投入 |
| D-12 | 当前平台不是小智官网完整平替 | 一期可以依赖小智官网/官方链路，但不能把我方业务控制权长期留在外部平台 |
| D-13 | 自研平台必须成为角色配置源 | 角色 prompt、voice_id、知识库引用等配置在我方平台维护，再人工或半自动同步到小智官网 |
| D-14 | 对话内容必须在自研平台体现 | 至少保存和展示设备、角色、用户输入、AI 回复、点位、知识片段摘要、时间和来源 |
| D-15 | 一期接受半自动同步小智官网 | 不强制自动调用小智官网 API，但必须有同步快照、状态和操作留痕 |

## 5.1 小智官网对标任务输入

本节是产品经理交给研发主管的任务评估输入，不包含工期、人员安排和技术实现方式。研发主管应基于本节拆分实施顺序、依赖关系、质量门和风险。

### 5.1.1 优先级口径

| 优先级 | 产品含义 | 研发主管需要评估 |
| --- | --- | --- |
| P0 | 我们商业化必须掌握的业务控制权，也是课题一期和市场化主线共用的核心资产 | 是否已覆盖当前一期；缺口是否阻塞演示和产品验收 |
| P1 | 近期对标小智控制台核心能力，减少人工配置和官网依赖 | 是否进入下一轮迭代；如何拆成可验证小任务 |
| P2 | 商业化前必须补齐的平台能力，面向真实批量设备和交付流程 | 是否需要单独里程碑；是否依赖架构决策 |
| P3 | 完全私有化或重型平台能力，适合商业化路径明确后立项 | 是否暂缓；需要哪些调研和前置验证 |

### 5.1.2 P0：必须先收回的业务控制权

| 任务输入 | 产品要求 | 验收口径 | 责任建议 |
| --- | --- | --- | --- |
| 设备业务档案 | 后台管理 device_id、SN、绑定角色、在线状态、版本摘要 | 能识别并展示当前演示设备，不依赖官网页面对外说明 | 研发主管拆解，架构/全栈支持 |
| 单设备单智能体绑定 | 一台设备同一时间只能绑定一个 agent_id | 设备详情、绑定页、演示页显示一致；普通用户无切换入口 | 研发主管拆解，架构/全栈支持 |
| 角色配置源 | 自研保存角色名称、人设 prompt、音色引用、知识库引用 | 至少 2 个角色可配置，设备/演示链路可读取 | 研发主管拆解，产品/全栈支持 |
| 三坊七巷数据集 | 自研保存多模态文旅数据库和向量检索入口 | 数据集、chunk、知识点、关联角色/点位状态可见 | 研发主管拆解，数据负责人/全栈支持 |
| GPS/NFC 业务闭环 | 自研保存点位、NFC、打卡记录和演示状态 | 1 个点位跑通 GPS 接近、NFC 确认、角色播报和记录展示 | 研发主管拆解，固件/全栈支持 |
| 自研演示/管理端 | 对外只展示我方业务页面 | PC/平板/手机能查看核心状态，非研发人员能看懂演示结果 | 研发主管拆解，前端/全栈支持 |
| 对话记录 | 自研平台承接用户输入、AI 回复和内容来源 | 能展示设备、角色、用户输入、AI 回复、点位、知识片段摘要、时间和来源 | 研发主管拆解，架构/全栈支持 |
| 官网同步状态 | 角色配置从我方平台生成，再同步到小智官网 | 能展示待同步、已同步、失败、最后同步时间、操作人和备注 | 研发主管拆解，架构/全栈支持 |
| 官网同步快照 | 展示或复制要填入小智官网的配置 | 能看到 prompt、voice_id、工具地址、知识库引用摘要 | 研发主管拆解，全栈支持 |
| 官网同步操作记录 | 半自动或人工同步必须留痕 | 能追溯谁在何时同步了哪个角色配置，失败原因可见 | 研发主管拆解，全栈支持 |

### 5.1.3 P1：近期对标小智控制台核心能力

| 任务输入 | 产品要求 | 验收口径 | 责任建议 |
| --- | --- | --- | --- |
| 设备配置下发 | 设备或模拟器从我方后台拉取角色、点位、NFC、数据集摘要 | 不需要研发手动改代码即可切换演示配置 | 研发主管评估，架构/全栈支持 |
| 设备在线状态和心跳 | 后台展示最近心跳、最近 GPS、最近打卡和异常状态 | 能判断设备是否在线、是否定位异常、是否打卡成功 | 研发主管评估，架构/全栈支持 |
| MCP/工具管理页 | 后台管理工具名称、用途、调用地址、启用状态 | 能看清小智侧或设备侧会调用哪些我方业务接口 | 研发主管评估，架构/全栈支持 |
| 工具调用日志 | 记录上下文、知识检索、打卡接口的调用时间和结果 | 出错时能定位是官网/工具/我方接口/数据集哪一环失败 | 研发主管评估，架构/全栈支持 |
| 官网配置辅助 | 降低人工在小智官网配置时的出错率 | 形成字段清单、复制内容或半自动同步说明 | 研发主管评估，全栈支持 |
| 角色配置版本 | 记录 prompt、音色、知识库引用变化 | 能看到最近更新时间和版本摘要 | 研发主管评估，全栈支持 |

### 5.1.4 P2：商业化前必须补齐的平台能力

| 任务输入 | 产品要求 | 验收口径 | 责任建议 |
| --- | --- | --- | --- |
| 设备激活/绑定流程 | 新设备通过我方流程完成激活、归属、绑定和初始化 | 不再完全依赖小智官网账号和设备码完成商业化交付 | 研发主管评估，架构主导 |
| 固件包管理 | 管理板卡型号、固件版本、下载包、变更说明和适用设备 | 研发/生产人员能找到正确固件包并知道适用范围 | 研发主管评估，固件/运维支持 |
| 烧录指引/交付流程 | 标准化烧录、验机、绑定和交付 | 新设备可按我方流程完成烧录和验收 | 研发主管评估，全栈/固件支持 |
| OTA/配置版本升级 | 管理升级版本、失败状态和回退策略 | 可按设备或批次管理升级，不靠临时手工沟通 | 研发主管评估，架构/固件支持 |
| 设备安全凭据 | 从静态 token 逐步升级到更安全的设备鉴权 | 设备接口不暴露明文密钥，日志脱敏 | 研发主管评估，架构/安全支持 |
| 多账号权限和审计 | 支持原厂、运营、内容、只读等角色 | 关键操作可追溯，不同账号操作边界清晰 | 研发主管评估，架构/全栈支持 |

### 5.1.5 P3：完整私有化或重型平台能力

| 任务输入 | 产品要求 | 验收口径 | 责任建议 |
| --- | --- | --- | --- |
| 自建语音服务端 | 自研或私有化 ASR/LLM/TTS、模型编排和语音网关 | 可脱离小智官网完成语音会话闭环 | 商业化立项后评估 |
| 完整设备云 | 支持批量设备长连接、消息下发、断线恢复和监控 | 面向真实批量设备稳定运行 | 商业化立项后评估 |
| 多租户/商业后台 | 支持组织、项目、客户、套餐、额度和运营看板 | 可服务不同客户或渠道 | 商业化立项后评估 |
| 计费/套餐/限流 | 按设备、模型、调用量或客户维度做额度治理 | 商业模式明确后可支撑收费和成本控制 | 商业化立项后评估 |

### 5.1.6 给研发主管的拆解提醒

研发主管后续拆任务时，需要特别注意：

1. P0 不是“完整小智官网复刻”，而是我方业务控制权必须闭环。
2. P1 是近期最像小智控制台的部分，重点在设备配置、角色配置、工具管理和日志。
3. P2 才进入固件包、烧录、激活、OTA、权限和安全凭据。
4. P3 不建议压进课题一期，也不建议在商业化路径不清楚前重投入。
5. 任何涉及固件烧录、设备激活、协议服务、OTA 的任务，需要架构师先补边界和方案，再由研发主管拆执行。
6. 对话记录和官网同步状态已经提升为 P0，不能只留在研发文档里作为后续任务；一期至少要做到“形式上完整、状态可见、留痕可查”。

## 7. 交接结论

产品侧当前已经明确：课题一期不是只做硬件接 GPS，也不是只做一个后台列表，而是要跑通“景区数据定制化智能体 + GPS 粗定位 + NFC 精准打卡 + 三端管理/演示页面 + 单设备单智能体绑定”的最小闭环。

后续角色补文档时，不能把以下内容整体下放到二期：

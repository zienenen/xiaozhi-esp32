# 开源选型与复用边界

文档状态：confirmed  
主责智能体：架构师智能体  
更新时间：2026-07-12

## 0. 阶段结论

一期采用“稳定、常见、团队容易接手”的开源组件组合，优先完成课题演示闭环，不建设完整商业化开源治理体系。

一期确定方向：

- 固件侧继续复用当前小智 ESP32 开源项目能力，`main/` 保持为固件主目录。
- 语音链路、设备接入和一期 MCP/工具入口继续依托 `xiaozhi.me`，作为不可见依赖。
- 自研业务后台采用 Django/DRF + PostgreSQL。
- 自研前端采用 React + Vite + Ant Design，不采用 Ant Design Pro 完整模板。
- 一期不启用 pgvector。
- 一期不引入 Docker Compose，只保留 `.env.example`、Nginx/Gunicorn 示例和部署说明。

完整许可证审计、供应链安全、SBOM、依赖漏洞治理、商业化分发合规、私有化语音服务端选型等内容，二期目前不做，商业化阶段再补充。

## 1. 选型原则

一期选型按以下优先级执行：

1. 优先使用项目已存在或已确认的技术栈。
2. 优先选择成熟、文档完善、全栈人员容易接手的组件。
3. 优先减少工程复杂度，避免为了未来商业化提前引入重平台。
4. 对商业化前必须补齐的合规、许可证、供应链风险，只记录边界和后续动作，不在一期展开治理。
5. 对小智官网能力只做接口级集成，不在一期复刻官网后台。

## 3. 一期不采用或暂缓的组件

| 组件/方向 | 当前结论 | 原因 |
| --- | --- | --- |
| Ant Design Pro 完整模板 | 一期不采用 | 模板能力偏重，容易引入权限、菜单、Mock、构建约束等额外复杂度 |
| pgvector | 一期不启用 | 先用普通 PostgreSQL 保存数据集状态和摘要，避免向量检索提前扩大范围 |
| Docker Compose | 一期不引入 | 当前是一台云服务器和本地 Demo，先用环境变量、Nginx/Gunicorn 示例即可 |
| Kubernetes | 一期不考虑 | 超出课题演示规模 |
| 自建小智服务端 | 一期不建设 | 语音链路继续依托 `xiaozhi.me`，自研后端只承载业务接口 |
| 小智官网全量复刻 | 一期不做 | 官网作为不可见依赖，对外展示自研业务页面 |
| 企业级网关/SSO/权限平台 | 一期不做 | 安全治理按最低边界处理，商业化阶段再补 |

## 4. 小智开源项目复用边界

当前仓库的小智 ESP32 开源项目是一期设备能力底座。

一期复用内容：

- 设备联网。
- 语音交互链路。
- 设备与小智官网或官方服务的接入方式。
- ESP-IDF 工程结构和板级基础能力。
- 后续接入 GPS、NFC、设备状态上报所需的固件扩展点。

一期不做内容：

- 不重写小智语音服务端。
- 不复刻小智官网控制台。
- 不把景点业务数据维护在小智官网。
- 不把角色 prompt 和知识库长期手工塞到官网后台。

一期集成方式：

```text
ESP32 小智固件
  -> xiaozhi.me 语音/MCP 能力
  -> 调用我方 Django 后端工具接口
  -> 返回角色上下文、景点知识、打卡结果
```

自研后端负责保存：

- 设备绑定。
- 角色配置源。
- 景点与 NFC 点位。
- 景区知识库摘要。
- 签到事件。
- 小智工具调用所需的上下文接口。

## 5. 后端选型边界

一期后端采用 Django/DRF + PostgreSQL，原因是：

- Python 技术栈能承接后续提示词、知识库处理、脚本任务和数据处理。
- Django 自带 ORM、Admin、认证、迁移体系，适合快速搭建业务后台。
- DRF 适合形成清晰 API 契约，方便设备、前端、模拟器、小智工具调用。
- PostgreSQL 稳定，后续需要向量检索时可再评估 pgvector。

一期不把 Django 扩展成大平台：

- 不做复杂 RBAC。
- 不做多租户。
- 不做计费。
- 不做完整审计。
- 不做异步任务平台，除非全栈实现时确有必要。

## 6. 前端选型边界

一期前端采用 React + Vite + Ant Design。

选择轻量组合而不是 Ant Design Pro 的原因：

- 当前页面目标是三端适配和演示闭环，不是完整企业后台。
- Vite 工程更轻，启动和构建更直接。
- Ant Design 组件足够支撑表单、表格、状态、配置页和演示页。
- 避免 Pro 模板带来的权限路由、菜单配置、Mock 体系和工程约束。

一期页面重点：

- 设备状态。
- 角色配置源。
- 景点/点位/NFC 管理。
- 数据集状态和摘要。
- 打卡记录。
- 演示态页面。

## 7. 部署选型边界

一期目标是一台云服务器或本地环境跑通。

当前采用：

- `.env.example` 说明环境变量。
- Nginx 示例配置。
- Gunicorn 示例配置。
- 前端 Vite build 后由静态服务或 Nginx 承载。
- 后端 Django/DRF 连接 PostgreSQL。

当前不采用：

- Docker Compose。
- Kubernetes。
- Helm。
- 多环境发布平台。
- 自动化蓝绿发布。

这些部署治理能力在商业化前再评估。

## 8. 许可证与供应链边界

一期只做基础认知，不做正式商业化许可证审计。

当前判断：

- 当前小智 ESP32 仓库根目录存在 MIT License，适合作为一期复用基础。
- Django、DRF、React、Vite、Ant Design、PostgreSQL 等均为常见开源组件，适合课题演示和内部研发。
- 具体依赖许可证以依赖包元数据、上游仓库和正式法务/安全审计结果为准。

一期最低要求：

- 保留上游 `LICENSE`。
- 不删除上游版权声明。
- 新增依赖要写入 `requirements.txt` 或 `package.json`。
- 不引入来源不明、无人维护、强 copyleft 风险不明确的组件。

商业化阶段再补：

- 完整 license 清单。
- SBOM。
- 依赖漏洞扫描。
- 许可证兼容性审计。
- 第三方服务条款审查。
- 开源组件升级策略。

## 9. 二期目前不做的内容

以下内容不进入当前阶段：

- 正式开源治理制度。
- SBOM 和供应链安全平台。
- 许可证自动扫描流水线。
- 商业化法务审计。
- 私有化小智服务端落地。
- 官网控制台全量复刻。
- 多租户 SaaS 平台依赖治理。
- 企业级依赖升级和漏洞响应 SLA。

这些内容等市场化或商业化启动后，由产品经理、研发主管、架构师、安全/法务角色共同评估。

## 10. 给全栈人员的落地要求

后端：

- 使用现有 `backend/requirements.txt` 管理 Python 依赖。
- 不擅自引入 Celery、Redis、pgvector、Elasticsearch 等重组件。
- 如果确需新增依赖，先说明用途、替代方案和是否影响部署。

前端：

- 使用现有 `frontend/package.json` 管理依赖。
- 继续采用 React + Vite + Ant Design。
- 不引入 Ant Design Pro 完整模板。
- 不引入复杂状态管理库，除非页面复杂度确实需要。

设备/固件：

- 保持小智 ESP32 上游结构可追踪。
- 产品逻辑扩展尽量和板级代码分离。
- GPS/NFC 扩展不应破坏原有语音链路。

部署：

- 先按单机部署说明推进。
- 不把 Docker Compose 作为一期必需交付。
- 不新增商业化运维平台依赖。

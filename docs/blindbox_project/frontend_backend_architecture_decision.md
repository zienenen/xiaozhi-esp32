## 2. 当前冲突

早期架构文档中存在过以下冲突，目前已按本文决策收敛：

| 冲突点 | 文档位置/表述 | 风险 |
| --- | --- | --- |
| 一期是否做业务后台 | `phase1_phase2_architecture_plan.md` 一处写“一期依托官网、二期建设自有后台和三端页面” | 会导致管理端、数据集状态、打卡记录被推迟 |
| 一期又推荐 Django/React | 同一文档技术建议处写“一期建议 Django + DRF + PostgreSQL + React” | 与“不做后台”形成冲突 |
| 全栈文档默认一期有后台 | `fullstack_implementation_guide.md` 以 Django + React + PostgreSQL 为一期落地方案 | 如果架构未确认，研发执行会无依据 |
| 产品 P0 要求三端页面 | PM 已确认三端管理、数据集状态、打卡记录、模拟打卡为 P0 | 如果一期无任何业务后台，需要其他方案承载这些 P0 |

因此本文回答的问题不是“产品要不要三端页面”，而是：

> 用什么最小技术形态承载已确认的产品 P0，同时不把一期做成完整商业平台。

## 3. 产品输入边界

以下为已确认产品边界，架构方案必须满足：

| 编号 | 产品要求 | 架构影响 |
| --- | --- | --- |
| P-01 | 景区数据集/向量库管理页为课题一期 P0 | 必须有数据集状态展示或等效可视化 |
| P-02 | 1 个景点点位完整跑通为 P0 | 需要点位配置、GPS 半径、NFC 标签和打卡结果 |
| P-03 | 手动模拟打卡页为 P0 | 需要测试入口和模拟数据标记 |
| P-04 | PC/平板/手机三端核心页面为 P0 | 需要响应式 Web 或等效方案 |
| P-05 | 单设备绑定单智能体 | 需要设备、角色、绑定关系的权威来源 |
| P-06 | GPS 粗定位 + NFC 精准打卡 | 需要设备端和业务侧共同处理状态 |
| P-07 | 语音链路不是当前业务后台的核心能力 | 后台不应承载实时音频流 |

## 4. 候选方案

### 4.1 方案 A：纯固件 + 官网控制台 + 静态配置

架构形态：

```text
ESP32 固件
  -> xiaozhi.me 官方语音服务
  -> 固件内置/JSON 配置
  -> 本地日志或串口展示
```

适用场景：

- 只验证 GPS/NFC 设备侧触发；
- 不要求三端管理页；
- 不要求数据集状态展示；
- 不要求打卡记录可视化。

优点：

| 优点 | 说明 |
| --- | --- |
| 最快 | 后端和前端工作量最低 |
| 语音风险低 | 继续使用小智官方链路 |
| 设备验证直接 | 固件团队可先跑通 GPS/NFC |

缺点：

| 缺点 | 影响 |
| --- | --- |
| 不满足三端 P0 | PC/平板/手机管理和演示页缺失 |
| 不满足数据集展示 P0 | 无法证明数据集、chunk、向量化状态 |
| 打卡记录弱 | 只能靠日志，验收证据不足 |
| 市场化复用弱 | 设备、角色、绑定能力无法沉淀 |

结论：

不建议作为当前完整一期方案。可作为固件最小联调子阶段，但不能覆盖已确认产品 P0。

### 4.2 方案 B：最小业务后台 + 响应式 Web + 官网语音链路

架构形态：

```text
ESP32 固件
  -> xiaozhi.me 官方语音服务
  -> 最小业务 API
  -> PostgreSQL 或等价持久化
  -> 响应式 Web 三端页面
```

适用场景：

- 一期需要三端管理和演示页面；
- 需要设备、角色、点位、NFC、打卡、数据集状态；
- 不想一期自建完整语音服务；
- 需要为市场化保留设备/角色/绑定能力。

优点：

| 优点 | 说明 |
| --- | --- |
| 满足产品 P0 | 覆盖三端、数据集状态、打卡记录、模拟打卡 |
| 语音边界清楚 | 后台只做业务，不承载实时语音 |
| 可迁移 | 后续可扩展为正式业务平台 |
| 验收证据充分 | 页面和记录可直接用于演示和答辩 |

缺点：

| 缺点 | 影响 |
| --- | --- |
| 工程量高于纯固件 | 需要后端、前端、部署联调 |
| 架构需收敛 | 必须明确 API、数据模型、权限和部署 |
| 数据治理提前出现 | 设备 ID、GPS、绑定关系、模拟数据需要安全边界 |

已选实现栈：

| 层级 | 决策 |
| --- | --- |
| 后端 | Django + Django REST Framework |
| 数据库 | PostgreSQL |
| 前端 | React + Vite + Ant Design 响应式页面 |
| 向量/数据集 | 一期不启用 pgvector；使用普通 PostgreSQL 保存数据集状态和片段摘要，后续如进入真实向量检索再评估 |

结论：

这是当前一期正式架构方案。数据集必须是真实数据，但格式和向量检索实现可在后续统一整改。

### 4.3 方案 C：本地 Mock 后台 + 静态 Web 演示页

架构形态：

```text
ESP32 固件
  -> xiaozhi.me 官方语音服务
  -> 本地 JSON / Mock API
  -> 静态 Web 页面
```

适用场景：

- 演示周期非常紧；
- 只需要页面看起来可用；
- 不要求真实数据库持久化；
- 硬件联调优先。

优点：

| 优点 | 说明 |
| --- | --- |
| 快 | 前端和固件可并行 |
| 低部署成本 | 可本地运行或静态托管 |
| 适合演示兜底 | 硬件未稳定时仍可展示流程 |

缺点：

| 缺点 | 影响 |
| --- | --- |
| 不是真后台 | 后续迁移成本高 |
| 数据可信度弱 | 打卡记录和数据集状态可能只是演示数据 |
| 容易误导验收 | 必须明确 Mock 标记 |

结论：

可作为应急演示或阶段性联调方案，不建议作为正式课题一期架构交付口径。

### 4.4 方案 D：自建小智服务端 + 业务后台一体化

架构形态：

```text
ESP32 固件
  -> 自建小智兼容语音服务
  -> 业务后台
  -> 数据库/向量库
  -> 三端页面
```

适用场景：

- 明确不依赖 `xiaozhi.me`；
- 需要私有化语音链路；
- 有足够研发资源维护语音服务；
- 商业化或数据闭环要求较高。

优点：

| 优点 | 说明 |
| --- | --- |
| 自主可控 | 语音、配置、业务可统一管理 |
| 长期扩展好 | 适合商业化平台 |
| 数据闭环完整 | 可统一采集设备和交互事件 |

缺点：

| 缺点 | 影响 |
| --- | --- |
| 一期过重 | 语音服务、业务后台、前端同时建设风险大 |
| 运维成本高 | 需要部署、监控、故障恢复 |
| 协议兼容风险 | 需要理解并维护小智服务端链路 |

结论：

不建议作为课题一期起点，可作为后续商业化或私有化阶段评估。

## 6. 架构决策

当前架构决策为：

> 方案 B：最小业务后台 + 响应式 Web + 官网语音链路。

已确认口径：

1. 一期新增最小业务后端，不做完整商业化平台。
2. 后端采用 Django + Django REST Framework。
3. 数据库采用 PostgreSQL。
4. 前端采用 React + Vite + Ant Design，不采用 Ant Design Pro 完整模板，用户侧采用同栈响应式页面。
5. 语音链路、设备接入和一期 MCP 可以继续依托 `xiaozhi.me`，官网页面作为不可见依赖。
6. 设备、角色配置源、点位、NFC、打卡记录和数据集状态进入自研后台。
7. GPS 只做附近提醒，不作为最终打卡依据；NFC 做精准确认。
8. 一期不复刻小智官网控制台，对外展示自研轻量页面和景区业务闭环。
9. 一期数据集使用真实景区数据，但不启用 pgvector；先用普通 PostgreSQL + 数据集状态/片段摘要展示，后续如进入真实向量检索再评估。
10. 设备配置以后端拉取为主，允许固件静态配置兜底。
11. 管理端一期使用演示账号，不建设完整登录权限体系。
12. GPS 不保存连续轨迹，只保存定位质量摘要，并按 10 秒级节流上报。
13. 角色 prompt、景点上下文和知识库由自研后台保存和生成；小智官网侧只配置工具/MCP 接入点，调用我方后端接口。
14. 一期 MCP/工具入口仍允许配置在小智官网侧，但工具能力指向我方业务配置、知识库查询和打卡接口。

仍需后续确认的架构边界：

1. 数据集最终格式、字段规范和前端统一整改方案。
2. 数据集最终格式、字段规范和前端统一整改方案。
3. 二期是否建设自研 MCP 管理页面、工具注册中心和官网配置自动化能力。

## 10. 当前结论

当前架构决策为：

1. 纯固件 + 官网控制台无法完整满足已确认产品 P0。
2. 一期直接自建完整小智语音服务过重。
3. 一期采用“Django/DRF + PostgreSQL + React/Vite/Ant Design + 官网语音/MCP 不可见依赖”的最小业务后台方案。
4. 二期再按市场化要求逐步建设自研设备智能体控制台和官网能力替代层。
